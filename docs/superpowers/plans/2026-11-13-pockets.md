# Pockets Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Detect blind pockets (the curtain-rail slot) in the DXFs, colour them in groups, set tool/depth/feeds per group, and write a pocket program `B<nn>P` per blank.

**Architecture:** `read_dxf` returns pockets on each `Shape`; a new `nesting/pockets.py` groups them and builds the cutter rings; `program.py` adds a `B<nn>P` program (ops carry their own tool, spindle and feeds, like drill ops already carry a tool); preview, run sheet, server storage and the page learn the new program and the group settings. The emitter keeps writing the same blocks.

**Tech Stack:** Python 3.11+ stdlib only, one HTML page, `unittest`.

**Spec:** `docs/superpowers/specs/2026-11-13-pockets-design.md` (also read the "Calls made in review" section). Existing code: `nesting/{settings,dxf,geometry,layout,program,preview,output,server,importdisk}.py`, `nesting/backends/cnc90.py`, `nesting/web/index.html`.

## Global Constraints

- Python stdlib only. Run the suite with `python3 -m unittest discover -s tests` (342 pass now); it must stay green after every task.
- The CNC90 emitter must still reproduce ZZT1, ZZT1AD and ZZT2A byte for byte; a program whose ops carry no per-op overrides is written exactly as before.
- Program names: 1-8 characters of `A-Z 0-9 _ -`; pocket program is `B<nn>P` (blank id + `P`). Order in lists, loader and run sheet: D, P, C.
- Depths are measured down from the top of the stack (scrap + blank). Pocket depth is measured from the blank's top face, which is the machined face (the DXF is the face-up view).
- Preview and program numbers come from the same model (existing rule). Y mirroring stays in `to_program` / `segs_to_program`.
- Hard errors: a depth that reaches the cups, a pocket depth above `panel.thickness - pocket.min_floor`, a pocket narrower than its tool, a pocket loop that crosses or lies outside the shape outline. Warnings only: a circle treated as a pocket, a pocket closer than the screw-head clearance to a screw or fixing hole, two pockets touching, more than 250 lines.
- No file, commit message or PR text may name the shop operator or mention Claude/AI; no `Co-Authored-By` line. Commit once per task on the current branch (`windows-start`); do not push.
- Nothing has run on the machine: docs must say pocket programs are format-checked and simulated only.

## Review Focus

- A DXF with a closed inner loop but no `POCKET` layer (a DXF not made by the export) still yields a pocket. (Task 2)
- A pocket narrower than its tool, and a pocket exactly as wide as the tool. (Task 4)
- A circle larger than `pocket.min_circle_diameter` becomes a pocket with a visible warning; one at or under it stays a hole; changing the parameter in the page re-reads the shapes. (Tasks 2, 7)
- Hand-edited `project.json` with an unknown pocket group, a missing field, or a non-numeric depth does not give a 500 and does not silently use a wrong value. (Task 7)
- An asymmetric plate: the mirrored DXF gives a mirrored outline and pocket, and the program-frame numbers of the pocket match the preview. (Tasks 2, 5, 6)

**Interfaces:**

### Task 4: Pocket cutter rings

**Files:** Modify `nesting/pockets.py`; tests in `tests/test_nesting_pockets.py`.

**Interfaces:**
- Produces: `class PocketError(ValueError)`; `pocket_rings(outline: list[Seg], tool_diameter: float, stepover_pct: float) -> list[list[Seg]]` — closed tool-centre rings in the same frame as `outline`, ordered from the innermost ring outward, the last ring being the wall ring (outline offset inward by the tool radius). Rings are produced by repeated inward offsets of `stepover = tool_diameter * pct / 100` while the offset still exists, plus enough rings that the union of cutter discs covers the whole pocket. A pocket exactly as wide as the tool (within 0.01 mm) gives a single degenerate ring (the centre line out and back as two lines) — decide the representation and document it in the docstring. A pocket narrower than the tool raises `PocketError('... narrower than the tool ...')`. Arcs stay arcs; arcs over 180 degrees are split (`split_large_arcs`). A circle pocket gives concentric circle rings.

- [ ] **Step 1:** Tests (use `geometry.sample`/`distance_to_chain`): `test_slot_20_wide_tool_12_gives_one_ring_at_offset_6`; `test_every_point_in_pocket_is_covered_by_cutter` (grid over the pocket: each point within tool radius of some ring); `test_cutter_never_leaves_pocket` (every ring point's distance to the pocket outline is >= radius - 0.01); `test_ring_order_inner_to_outer_wall_last`; `test_wider_pocket_gets_several_rings_with_stepover` (60 x 40 pocket, 8 mm tool, 40%); `test_pocket_equal_to_tool_width`; `test_pocket_narrower_than_tool_is_an_error`; `test_round_pocket_rings_are_concentric_arcs`.
- [ ] **Step 2:** Implement using `geometry.offset_outline(segs, r, outward=False)`; catch `OffsetError` as "collapsed". Full suite; commit "Add pocket cutter rings".
